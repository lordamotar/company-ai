# AIKOS CRM Intelligence — Речевая и текстовая аналитика

Комплексная система мониторинга, транскрибации, многоуровневого анализа речи (Tone of Voice) и текстовых диалогов клиентов компании AIKOS.

---

## Архитектура системы

```text
   incoming/ (аудио с АТС)                      dialog/ (CSV из Битрикс24)
          │                                              │
          ▼                                              ▼
   worker.py  (Gemini API)                        dialog_processor.py
   worker-openrouter.py  (OpenRouter)                    │
          │                                              ▼
          │  один мультимодальный запрос:          dialogs_data.json / dashboard.html
          │  аудио + prompts/unified_analysis_prompt.md
          │  → расшифровка, тональность, CSAT, чек-лист,
          │    коммерция, категория звонка (JSON)
          ▼
   ton_voice_processor.save_unified_analysis
          │  + librosa: громкость, паузы, темп речи
          ▼
   PostgreSQL (Docker, порт 5433)
          │
          ▼
   FastAPI (server.py / app/) ──► веб-интерфейс frontend/ (порт 8080)
```

Оба воркера работают одинаково и отличаются только провайдером модели. Промпт у них общий.
На боевом сервере останется один воркер (см. `docs/LOCAL_SERVER.md`).

## Что извлекается из звонка

1. **Расшифровка** — дословные реплики «Менеджер / Клиент» с таймкодами (веб-плеер с перемоткой по репликам).
2. **Тональность и эмоция каждой реплики** — из ответа модели.
3. **Акустика** — громкость (RMS), доля тишины, громкие моменты, темп речи (`librosa` + таймкоды реплик).
4. **Оценка разговора** — CSAT (1–5), вежливость менеджера (1–5), конфликт и его причина, краткий вывод.
5. **Чек-лист скрипта продаж** — 7 пунктов с цитатами, статусы «пройден / не пройден / неприменимо».
6. **Коммерция** — итог звонка (`sale_status`), сумма, допродажа, запись на сервис, бренд, типоразмер, сезон, город.
7. **Категория звонка** — по справочнику `call_categories.py` (см. ниже).

> Модели wav2vec2 и RuBERT из ранних версий в текущем пайплайне не используются
> (их код остался в `ton_voice_processor.py`, но нигде не вызывается).

## Промпты

Промпты хранятся в `prompts/` в виде Markdown, их можно править без изменения кода:

* `prompts/unified_analysis_prompt.md` — анализ звонка, общий для `worker.py` и `worker-openrouter.py`.
  Метка `{{CATEGORIES}}` при загрузке заменяется справочником категорий (`prompt_loader.py`).
* `prompts/manager_analysis_prompt.md` — AI-отчёт по менеджеру в веб-интерфейсе.

Любая правка текста промпта автоматически даёт новую версию (`prompt_version`), поэтому результаты
до и после правки можно сравнить на эталоне (`golden_set.py report`). Воркер нужно перезапустить.

## Структура проекта

* `incoming/` — входящие аудиозаписи звонков (`.mp3`, `.wav` и др.).
* `processing/`, `processed/`, `error/` — директории жизненного цикла обработки файлов.
* `transcriptions/` — текстовые расшифровки звонков.
* `prompts/` — промпты моделей (см. выше).
* `worker.py` / `worker-openrouter.py` — воркеры анализа новых записей (Gemini API / OpenRouter).
* `ton_voice_processor.py` — сохранение результата анализа во все таблицы, расчёт акустики.
* `call_categories.py` — справочник категорий звонков.
* `lead_scoring.py` — оценка клиента и следующий шаг (выключено, см. ниже); `migrations/` — дополнительные миграции.
* `tire_sizes.py` — проверка типоразмеров: продиктованные номера телефонов и заказов не принимаются за размер шины.
* `analysis_runs.py` — версии анализа (модель, промпт) и обезличенная отправка файла.
* `golden_set.py` — эталонный набор звонков и отчёт о точности моделей.
* `manager_registry.py`, `managers.json` — справочник менеджеров.
* `reprocess_calls.py` — перепрогон звонков с неполным анализом; `retry_errors.py` — возврат файлов из `error/` в очередь.
* `reset_database.py` — очистка таблиц звонков (осторожно: удаляет данные).
* `export_db_to_json.py` — выгрузка данных для дашборда (`frontend/calls_data.json`).
* `dialog/`, `dialog_processor.py` — текстовые диалоги Bitrix24 / WhatsApp (CSV) и их дашборд.
* `server.py` / `app/` — FastAPI бэкенд (REST API, аудиостриминг, аудит правок).
* `frontend/` — веб-интерфейс аналитики звонков, профили менеджеров, журнал аудита.
* `docs/` — документация (`LOCAL_SERVER.md` — переход на локальный сервер).
* `.tech/` — разовые скрипты, заметки и SQL-исправления (не в git).
* `docker-compose.yml` — PostgreSQL (5433), n8n (5678), web (8080).

## Настройки подключения и окружения

Параметры считываются из переменных окружения или `.env`:
* `DB_HOST` (по умолчанию `127.0.0.1`, в Docker: `postgres`)
* `DB_PORT` (по умолчанию `5433`, внутри Docker: `5432`)
* `DB_NAME` (`company`)
* `DB_USER` (`company_user`)
* `DB_PASSWORD` (`company_password`)
* `GEMINI_API_KEY_1`, `GEMINI_API_KEY_2`, … — ключи Google Gemini API (при исчерпании квоты воркер переключается на следующий)
* `GEMINI_MODELS` — модели Gemini через запятую, по приоритету
* `OPENROUTER_API_KEY`, `OPENROUTER_MODELS` — ключ и модели для `worker-openrouter.py`
* `MAX_RETRIES` (3), `FILE_READY_TIMEOUT` (30 сек) — повторы и ожидание докопирования файла
* `PORT` — порт веб-сервера (по умолчанию `8080`)

## Быстрый старт

### 1. Запуск инфраструктуры (Docker)
```powershell
docker compose up -d
```

### 2. Применение миграций БД (при первом запуске)
```powershell
.venv\Scripts\python apply_migrations.py
```

### 3. Запуск фонового воркера речевой аналитики
```powershell
.venv\Scripts\python worker.py               # через Gemini API
.venv\Scripts\python worker-openrouter.py    # или через OpenRouter
```
Миграцию (шаг 2) нужно повторять после обновления кода — она безопасна и данные не трогает.

### 4. Запуск веб-сервера дашборда
```powershell
.venv\Scripts\python server.py
```
После запуска интерфейс доступен по адресу: **`http://localhost:8080`**  
Документация Swagger UI: **`http://localhost:8080/docs`**

### 5. Анализ текстовых диалогов Bitrix24 (WhatsApp)
```powershell
.venv\Scripts\python dialog_processor.py
```
Для непрерывного мониторинга новых выгрузок CSV:
```powershell
.venv\Scripts\python dialog_processor.py --watch
```

## Версии анализа и эталонный набор (golden set)

После `python apply_migrations.py` каждый анализ звонка сохраняется с провайдером, моделью и версией промпта
(`call_transcriptions.analysis_*`, история — в `call_analysis_runs`). В Gemini отправляется копия аудио
с нейтральным именем файла: номер телефона и дата из имени файла АТС в облако не уходят
(в OpenRouter аудио передаётся без имени файла). Содержание разговора при этом уходит в облако —
это ограничение тестового режима до перехода на локальные модели.

Проверка качества моделей на звонках, размеченных РОПом:
```powershell
.venv\Scripts\python golden_set.py template --last 150          # CSV для разметки в Excel
.venv\Scripts\python golden_set.py import golden_template.csv --by "Имя РОПа"
.venv\Scripts\python golden_set.py rerun --provider gemini      # проверочный прогон, боевые данные не меняются
.venv\Scripts\python golden_set.py report --details             # точность по полям и чек-листу
```

Что нужно для перехода на локальный сервер и локальные модели — `docs/LOCAL_SERVER.md`.

## Категории звонков

Единый справочник — `call_categories.py`: «Подбор и покупка», «Уточнение по товару», «Заказы и брони», «Сервис»,
«Справка», «Жалоба», «Не клиентский звонок», «Прочее». Категория — тема звонка, итог (бронь/отказ) — в `sale_status`.
Справочник подставляется в промпт (`{{CATEGORIES}}`), ответ модели приводится к нему при сохранении.
Для «Не клиентского звонка» все пункты чек-листа — «неприменимо»: такие разговоры не влияют на оценку менеджеров.
Фильтр и цвета в `frontend/` держать в соответствии со справочником.

Переразметка звонков по справочнику выполнена 01.10.2026 разово; скрипт `reclassify_categories.py`,
отчёт и ручные исправления (`fix_categories_2026-10-01.sql`) лежат в `.tech/`. Для повторного запуска
скрипта (например, после изменения справочника) скопируйте его обратно в корень проекта.

## Оценка клиента и следующий шаг (подготовлено, ВЫКЛЮЧЕНО)

Модуль `lead_scoring.py` + блок промпта `prompts/lead_scoring.md`:
* оценка клиента: **A** (готов купить / бронь), **B** (откладывает), **C** (узнаёт цены), **D** (покупка маловероятна), **Нецелевой**;
* причина нецелевого звонка — из фиксированного списка (для чистки рекламы);
* следующий шаг: тип из списка, описание, срок, кто делает (менеджер / клиент).

Пока `ENABLE_LEAD_SCORING` не `true`, блок не попадает в промпт (версия промпта не меняется) и поля не сохраняются.

Включение:
```powershell
.venv\Scripts\python apply_migrations.py migrations/lead_scoring.sql   # колонки lead_grade, lead_grade_reason, non_target_reason, next_step
# в .env:  ENABLE_LEAD_SCORING=true
# перезапустить воркер
```
Перед использованием в отчётах проверить точность новых полей на эталоне РОПа.
Не сделано (следующий этап, после автоматической загрузки с АТС и статистики CDR): показ полей в интерфейсе,
уведомления руководителю «шаг обещан и не выполнен» (через n8n в Telegram / Битрикс24), отчёт причин для маркетинга.

### Подключение DataLens к PostgreSQL проекта:
* **Хост**: `host.docker.internal`
* **Порт**: `5433`
* **Имя БД**: `company`
* **Пользователь**: `company_user`
* **Пароль**: `company_password`
