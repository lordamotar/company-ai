# Переход на локальный (боевой) сервер: что нужно

Состояние на 01.10.2026. Сейчас система работает в тестовом режиме на облачных моделях
(Gemini, OpenRouter) и анализирует только звонки. Этот документ — список того, что нужно
для работы на собственном сервере без облачных моделей, и порядок перехода.

---

## 1. Что уже подготовлено в коде (тестовый режим)

- **Версии анализа.** У каждого звонка в `call_transcriptions` записаны `analysis_provider`,
  `analysis_model`, `prompt_version`, `analyzed_at`. Все прогоны (боевые и проверочные)
  хранятся в `call_analysis_runs` с полным JSON-ответом модели и временем обработки (`duration_ms`).
  Версия промпта — хеш его текста: любая правка промпта автоматически даёт новую версию.
- **Эталонный набор (golden set).** Таблица `golden_calls` и скрипт `golden_set.py`:
  РОП размечает звонки в CSV (Excel), модели прогоняются по этим звонкам, отчёт показывает точность
  по каждому полю и пункту чек-листа. Проверочные прогоны боевые данные не меняют.
- **Обезличенная отправка в Gemini.** В облако уходит временная копия аудио с нейтральным именем,
  без номера телефона и даты из имени файла АТС. Важно: само аудио и содержание разговора
  в облако всё равно уходят — это ограничение облачного теста, и снимается оно только переходом на локальные модели.
- **wav2vec2 в боевом пайплайне уже не используется.** Эмоции и тональность реплик берутся из ответа модели
  (`save_unified_analysis`). Разделы README про wav2vec2/RuBERT описывают старый пайплайн.

Перед использованием: `python apply_migrations.py` (миграция идемпотентна, данные не трогает).

---

## 2. Чем локальный анализ отличается от облачного

Облако: **один** мультимодальный вызов — аудио → готовый JSON (диалог, оценки, чек-лист, коммерция).

Локально это **два шага**:

1. **Распознавание речи (ASR)** → реплики с таймкодами и спикерами (`dialogue`).
2. **Текстовая LLM** по расшифровке → `overall_sentiment`, `commercial`, `checklist`,
   тональность и эмоция каждой реплики (по тексту, без интонации).

JSON-схема ответа остаётся прежней, поэтому `save_unified_analysis`, база, веб-интерфейс и отчёты не меняются.

Что нужно дописать в коде к моменту перехода:

- провайдер `local`: модуль ASR на faster-whisper + клиент OpenAI-совместимого API (vLLM);
- текстовую версию промпта: без «прослушай аудиозапись» и без блока `acoustics` (акустику считает librosa);
- `golden_set.py rerun --provider local` (точка подключения уже заложена);
- один воркер вместо двух, провайдер выбирается в `.env` (например `ANALYSIS_PROVIDER=gemini|openrouter|local`).

## 3. Модели

**Распознавание речи**
- Основной кандидат: faster-whisper `large-v3` (русский + казахский; на GPU).
- Для сравнения: GigaAM (сильная русская модель), казахские модели ISSAI.
- Выбор — по 20–30 звонкам с вручную выверенной расшифровкой (русские, казахские, смешанные).

**Разделение спикеров (кто говорит — менеджер или клиент)**
- Лучший вариант — **стерео-запись в Asterisk** (MixMonitor с раздельной записью каналов):
  менеджер и клиент в разных дорожках, диаризация не нужна, ошибок «кто что сказал» нет.
  Включить при переезде, пока АТС всё равно перенастраивается.
- Если записи останутся моно — диаризация (например pyannote): медленнее и с ошибками.

**Смысловой анализ (LLM)**
- Открытая модель на 25–35 млрд параметров с хорошим русским языком
  (актуальные на момент закупки версии семейств Qwen, Gemma и аналогов), запуск через vLLM.
- Модель выбирается **не заранее**, а по отчёту `golden_set.py report`: 2–3 кандидата
  прогоняются по эталону, сравниваются с Gemini и между собой.

## 4. Железо

**Сначала посчитать нагрузку:** выгрузить из CDR Asterisk реальное число звонков в день
и среднюю длительность. Ориентир: 1000 звонков × 3 мин = 50 часов аудио в сутки;
faster-whisper на GPU работает в 15–40 раз быстрее реального времени, то есть
это 75–200 минут работы карты на распознавание в сутки. Время LLM-анализа видно
по `duration_ms` в `call_analysis_runs` после пилотных прогонов.

**Рекомендуемая конфигурация (продакшен)**
- 1 GPU с 48 ГБ памяти (класс NVIDIA L40S / RTX 6000 Ada): ASR и LLM ~30B в квантовании на одной карте.
  H100 для этих объёмов избыточна.
- CPU 16+ ядер, RAM 64 ГБ.
- NVMe 1–2 ТБ. Аудио: ~0,45 МБ на звонок в mp3 → при 1000 звонках в день ≈ 160 ГБ в год.
- Отдельный диск или сервер для резервных копий.

**Пилот:** карта на 24–32 ГБ (RTX 4090 / 5090) и модель поменьше — для проверки схемы, не для боя.

**Программное окружение:** Ubuntu Server LTS, драйвер NVIDIA + CUDA, Docker + NVIDIA Container Toolkit.

## 5. Инфраструктура и запуск

- Все сервисы в `docker compose` с `restart: unless-stopped`: postgres, web, worker, vllm.
  n8n — только когда появятся реальные сценарии (сейчас в нём нет ни одного workflow).
- Данные Postgres — в docker volume или на отдельном диске, не в папке проекта.
- Очередь: воркер берёт задачи из таблицы (`SELECT … FOR UPDATE SKIP LOCKED`),
  папка `incoming/` — только точка доставки файлов. Перезапуск не теряет задачи, можно запустить несколько воркеров.
- Доставка записей с АТС: сразу после окончания записи (хук в dialplan) или по расписанию (rsync/SMB).
- Ротация логов (`worker.log` сейчас растёт без ограничения).
- Мониторинг: хотя бы проверка «воркер жив» и «очередь не растёт» с уведомлением.

## 6. Безопасность (обязательно до выхода в бой)

- Авторизация в веб-интерфейсе, роли (РОП, руководитель, администратор).
- Сменить пароли из `docker-compose.yml` (Postgres `company_password`, n8n `admin123`) и вынести их в `.env`.
- Порты 5433, 5678, 8080, 8088 — только из локальной сети или через VPN; веб — через HTTPS (nginx/Caddy).
- Резервные копии: `pg_dump` ежедневно + копия аудио на другой диск/сервер; раз в месяц проверять восстановление.
- Определить срок хранения записей и расшифровок.

---

## 7. Персональные данные

- После перехода удалить облачные ключи из `.env` и закрыть воркеру исходящий доступ к внешним API (firewall).
- Номера телефонов есть в именах файлов, логах и базе — доступ только у тех, кому нужен.
- Требования закона РК о персональных данных (хранение на территории РК, трансграничная передача, согласие)
  — оценить с юристом. Отдельно зафиксировать решение по записям, отправленным в облако во время теста.

## 8. Порядок перехода

1. **Сейчас, в облаке:** применить миграцию; собрать эталон из 100–150 звонков
   (русские / казахские / смешанные; продажи, брони, отказы, жалобы; короткие и длинные);
   получить базовую точность Gemini: `golden_set.py rerun --provider gemini`, затем `report`.
2. **Сервер:** развернуть окружение, перенести базу, включить стерео-запись в Asterisk.
3. **Локальный провайдер:** дописать (раздел 2), прогнать эталон 2–3 кандидатами LLM, выбрать модель.
4. **Критерии приёмки** — согласовать с руководством заранее. Например: итог звонка ≥ 85%,
   бренд и типоразмер ≥ 80%, пункты чек-листа ≥ 80%, CSAT с допуском ±1 ≥ 85%,
   и не хуже Gemini больше чем на 5 пунктов. Цифры условные — их задаёт бизнес.
5. **Параллельная работа 1–2 недели:** локальная модель в бою, РОП выборочно сверяет.
6. Отключить облачные ключи.
